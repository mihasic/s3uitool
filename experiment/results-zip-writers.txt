Zip writer comparison — one 200 MiB object, same probe harness (experiment/zipstore-probe.ts),
macOS `/usr/bin/time -l` maximum resident set size. Bun baseline ~40 MiB.

writer                        content          archive bytes    maxRSS
----------------------------------------------------------------------
client-zip 2.5.0 (STORE)      incompressible     209,715,330    254 MiB
client-zip 2.5.0 (STORE)      compressible       209,715,330    416 MiB
fflate ZipDeflate level 0     incompressible     209,732,820    533 MiB
fflate ZipDeflate level 0     compressible       209,732,610    518 MiB
fflate ZipDeflate level 6     incompressible     209,775,180    882 MiB
fflate ZipDeflate level 6     compressible           613,994    680 MiB

In-server peak RSS for GET /download-prefix on the same objects (baseline 71 MiB):

  implementation                                   incompressible   compressible
  buffer-whole-object + push from start()              2911 MiB        710 MiB
  stream per chunk + pull-driven backpressure   ->      989 MiB        778 MiB
  plain GET /download of the same object (no zip)       201 MiB              -

Conclusion: the streaming/backpressure fix removed 2/3 of the peak with no
dependency and no loss of compression. client-zip is leaner still, but only
because it never compresses: on compressible content it ships a 209 MB archive
where DEFLATE ships 0.6 MB — a 341x regression on exactly the content this tool
is most often used to download (logs, JSON, config, source).

FOLLOW-UP: Bun native CompressionStream("deflate-raw") + Bun.hash.crc32, with
fflate writing only the zip container (ZipInputFile). A/B over identical S3
prefixes, same process, same run:

corpus                          fflate                       native
--------------------------------------------------------------------------------
200 real-text files, 50 MiB     1.02s  82,287 B  stall 11ms  0.58s  75,822 B  3ms
200 lorem-repeat files, 50 MiB  0.99s 164,642 B  stall 15ms  0.57s 335,949 B  3ms
1 x 200 MiB compressible        1.94s 613,799 B  stall  9ms  0.78s 1,216,824 B 7ms

In-server peak RSS for GET /download-prefix (baseline 87 MiB):

  200 MiB compressible     fflate 778 MiB   ->  native 130 MiB
  200 MiB incompressible   fflate 989 MiB   ->  native 728 MiB
  /api/health latency while a 200 MiB zip streams: 2 ms

Native is faster in every case and 8% smaller on realistic text; it is larger only
on pathologically repetitive input, where fflate's level 6 finds longer matches.
Archives verified with system unzip, zipinfo, Python zipfile and fflate unzipSync.
